# Переводы каталога

Каталог заведён на русском: названия разделов, характеристик и карточек пришли
из источника по-русски, а поля `name_kk` и `name_en` импорт оставляет пустыми —
пустое поле означает «перевода нет», и витрина честно откатывается на русское.

Здесь лежат сами переводы и то, чем они накатываются.

## Устройство

| Файл               | Что это                                                            |
| ------------------ | ------------------------------------------------------------------ |
| `glossary.json`    | Переводы. Ключ — РУССКАЯ СТРОКА, значение — казахский и английский |
| `extract.mjs`      | Выписывает из базы то, чего в глоссарии ещё нет                    |
| `build-sql.mjs`    | Собирает из глоссария `translations.sql`                           |
| `translations.sql` | Готовый набор UPDATE. Собирается, а не правится руками             |

**Ключ — русский текст, а не идентификатор.** Идентификаторы меняются при каждом
повторном импорте, а текст — нет. Поэтому глоссарий переживает пересборку стенда
и накатывается на неё заново без правок. По той же причине один перевод
покрывает все повторы: «Мощность двигателя» встречается у двадцати семи
характеристик разных разделов, и переводится один раз.

## Как накатить

```bash
node dump/i18n/build-sql.mjs
docker exec -i techline-postgres psql -U postgres -d techline -f - < dump/i18n/translations.sql
docker exec techline-cache redis-cli FLUSHALL   # иначе API отдаёт прежние названия из кэша
```

## Как дополнить

```bash
node dump/i18n/extract.mjs        # выпишет непереведённое в dump/i18n/missing.json
```

Заполнить и перенести в `glossary.json`, затем собрать SQL заново.

## Названия машин переводятся не целиком

Название карточки — это «русский тип + латинское обозначение»: «Гусеничный
экскаватор XE370G». Переводится только тип, обозначение остаётся как есть —
XE370G одинаково на любом языке, и «переводить» его значило бы портить.
Поэтому в глоссарии лежат 144 типа, а не 426 названий.

## Единицы измерения

В базе единица лежит ОДНИМ столбцом на все языки, и это правильно: единица —
обозначение, а не текст. Она не переводится, а записывается принятой в языке
нотацией, и соответствие «кН → kN» однозначно. Поэтому в базу единицы
не пишутся: `build-sql.mjs` собирает из глоссария таблицу для витрины
(`src/lib/i18n/units.generated.ts`), и та подставляет нужную нотацию при
показе. Источник остаётся один — этот глоссарий.

В источнике одна и та же величина записана в шести вариантах: «кН·м», «кН.м»,
«т·м», «т•м», «тм», «т.м.». Глоссарий переводит их все, но НЕ приводит
к одному виду в русском: это правка данных, а не перевод, и делать её надо
в импорте.

**Единица переключается не везде.** У характеристик с типом `string` значение
пришло из источника одной строкой вместе с единицей — «33 500 кг», — а столбец
`unit` у них пуст. Такие значения остаются как есть: разбирать их на число
и единицу значило бы переписывать данные, а не показывать их. Там, где единица
лежит отдельным полем — у числовых характеристик, по которым работают
фильтры, — она переключается.

## Что осталось непереведённым

Характеристик в каталоге 610 различных названий. Переведены все фильтруемые,
кроме одной, и самые частые из остальных. Непереведённые — длинный хвост
названий, встречающихся у одной-двух карточек и видных только в таблице
характеристик.

Отдельно помечены названия, которые ломать перевод не стоит, потому что
сломан сам РУССКИЙ оригинал: «Дать процесс», «Быстро увеличить скорость»,
«Гидравлический банк» (это бак), «Джойстиковая кол-во секций стрелы». Они
пришли машинным переводом с китайского на сайте-источнике. Их надо чинить
по-русски, а не переводить дальше — список лежит в `glossary.json`
под ключом `_suspect`.
