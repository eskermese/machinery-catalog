# techline

Каталог спецтехники: карточки с ценами в долларах, пересчёт в тенге по курсу
с наценкой, калькулятор лизинга, коммерческие предложения по публичной ссылке
и заявки с сайта. Админка живёт в том же сервисе: вход по номеру телефона,
роли менеджера и администратора.

## Стек

Go 1.26, PostgreSQL 17 (pgx/v5, миграции golang-migrate), Dragonfly как
Redis-совместимый кэш, chi для HTTP, `shopspring/decimal` для курсов,
Prometheus и Pyroscope для наблюдаемости.

## Архитектура

Гексагональная: зависимости направлены внутрь, к домену.

```
transport/http ──┐
                 ├──► service ──► domain (entity, form, presenter, leasing)
worker ──────────┘        │
                          ▼
                  storage/repository (порты)
                          │
              ┌───────────┴───────────┐
        storage/postgres        storage/dragonfly
```

- **`internal/domain`** — правила. Не знает ни про HTTP, ни про SQL, ни про
  конфигурацию. `leasing` внутри него не знает даже про остальной домен:
  это чистый калькулятор, вход и выход — целые минорные единицы.
- **`internal/service`** — сценарии. Оркеструет домен через порты; какая за
  портом база или кэш, ему неизвестно.
- **`internal/storage/repository`** — исходящие порты, объявленные интерфейсами.
  Реализации (`postgres`, `dragonfly`) прячут SDK и схему хранения.
- **`internal/transport/http`** — разбор запроса, аутентификация, проверка роли,
  вызов сервиса, отображение ответа. Бизнес-правил здесь нет.
- **`internal/worker`** — фоновые задачи: загрузка курса, разбор очереди
  уведомлений.

Подробные соглашения — в `CLAUDE.md`.

## Локальный запуск

```bash
make compose        # postgres, dragonfly, prometheus, pyroscope и сам сервис
make compose-down   # остановить
```

Сервис поднимается на `:8000`, PostgreSQL на `:5432`, Dragonfly на `:6379`,
Prometheus на `:9090`, Pyroscope на `:4040`.

Миграции накатываются отдельно, DSN — через переменную окружения:

```bash
export DATABASE_URL='postgres://postgres:postgres@localhost:5432/techline?sslmode=disable'
make migrate-up        # накатить
make migrate-down      # откатить последнюю
make migrate-new name=<имя>
```

Чтобы войти администратором, номер нужно завести заранее — переменной
`ADMIN_PHONES`: самостоятельная регистрация означала бы, что права раздаёт
тот, кто их запрашивает. Менеджер входит свободно, учётная запись создаётся
при первом входе.

Инструменты (`migrate`, `mockgen`, `swag`, `golangci-lint`, `gofumpt`)
ставятся один раз:

```bash
make bin-deps
```

## Тесты

```bash
make test         # unit, с -race и покрытием
make lint         # golangci-lint
make all          # fmt tidy swag mock lint test — перед MR
```

Интеграционный набор поднимает собственные контейнеры через dockertest,
собирает образ сервиса и гоняет по нему живой HTTP:

```bash
make integration
```

Требует запущенного Docker. Набор идемпотентен: контейнеры между прогонами
переиспользуются, поэтому данные сеются так, чтобы повторный запуск не падал
на уникальных ключах.

## Структура

```
cmd/app            точка входа сервиса
cmd/migrate        прогон миграций
config/            YAML-конфигурация окружений
integration-test/  end-to-end тесты на живых контейнерах
internal/          код сервиса (см. «Архитектура»)
migrations/        SQL-миграции golang-migrate
pkg/               переиспользуемое: логгер, кэш, ошибки, метрики, HTTP-клиенты
swagger/           сгенерированный OpenAPI
```

## API

Спецификация генерируется из аннотаций в обработчиках:

```bash
make swag
```

Результат — в `swagger/`, у поднятого сервиса открывается на
`http://localhost:8000/swagger/index.html`.

Публичная часть смонтирована на `/api/v1`, административная — на
`/api/v1/admin` за проверкой роли. Сервисные ручки (`/version`, `/metrics`,
`/files`, `/swagger`) стоят вне аутентификации.
