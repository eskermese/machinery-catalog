# Руководство по репозиторию

## Минимализм (YAGNI)
Перед тем как писать код, спускайся по лестнице и остановись на первой подходящей ступени:
1. Нужно ли это вообще? → нет: пропусти (YAGNI).
2. Есть в stdlib? → используй.
3. Нативная возможность платформы? → используй.
4. Уже установленная зависимость решает? → используй, не добавляй новую.
5. Можно одной строкой? → одна строка.
6. Только потом — минимум кода, который работает.

## Домен
Сервис — каталог спецтехники: карточки с ценами в долларах, пересчёт в тенге
по курсу с наценкой, калькулятор лизинга, коммерческие предложения по публичной
ссылке и заявки с сайта. Админка живёт в том же сервисе.

Не описывай здесь сущности, которых ещё нет в коде: раздел пополняется вместе
с реализацией, а не впереди неё.

### Сущности

- **Учётные записи** (`user.go`, таблица `users`). Роли (`entity.ActorType`):
  `manager`, `admin`, `system`. Токен выпускается только менеджеру
  и администратору (`entity.IsLoginRole`); `system` принадлежит самому сервису
  и входом не пользуется.
- **Каталог** (`catalog.go`, `catalog_search.go`): `Category` — дерево,
  `Attribute` + `AttributeOption` — характеристики категории,
  `Machine` + `MachineImage` + `MachineAttributeValue` — карточка.
  Характеристики хранятся EAV: `attributes` объявляет тип, значения лежат
  в `machine_attribute_values`.
- **Курс** (`fx.go`): `FXRate` — чистый курс источника, `FXMarkup` — история
  наценки, `AppliedFXRate` — то, что получилось из них вместе.
- **Лизинг и предложения** (`leasing_program.go`, `quote.go`):
  `LeasingProgram` — границы партнёрской программы, `Quote` — выпущенное КП
  вместе с полным входом и результатом расчёта.
- **Заявки** (`lead.go`): `Lead` со стадиями обработки.
- **Расчёт** (`internal/domain/leasing`) — отдельный пакет, чистая функция
  `Calculate`. Не знает ни про остальной домен, ни про программы, ни про валюты.

### Правила, которые нельзя обойти

- **Администратор не регистрируется сам.** Менеджер входит свободно, учётная
  запись создаётся при первом входе; администратор входит, только если номер
  заведён заранее через `ADMIN_PHONES`. Иначе права раздавал бы тот, кто их
  запрашивает.
- **Публикация карточки — два признака сразу**: `is_active` и непустой
  `published_at`. Витрина требует обоих (`Machine.IsPubliclyVisible`).
  Повторная публикация дату не сбрасывает: `published_at` задаёт порядок ленты,
  и возвращённая карточка не должна всплыть как новинка.
- **Скрытая цена опускается целиком**, а не отдаётся нулём: при
  `is_price_public = false` поля цены в ответе просто нет.
- **Цикл в дереве категорий** отвергает триггер `categories_reject_cycle_trg`,
  а не только сервис: цена ошибки — бесконечная рекурсия в обходе поддерева.
- **Курса нет — отказ, а не единица.** Подстановка `1` продала бы технику
  по цене в долларах как за тенге. Вчерашний курс при этом штатен: он
  возвращается вместе со своей датой, и решает потребитель.
- **Курс append-only.** Строка `fx_rates` описывает курс, который уже показали
  клиенту; переписывать её задним числом нельзя. Наценка живёт отдельной
  таблицей именно поэтому.
- **КП фиксирует всё в момент выпуска**: цену, курс, дату курса, наценку,
  параметры расчёта и полный график. Клиент и менеджер обязаны видеть одну
  цифру спустя недели, поэтому ничего не пересчитывается при чтении.
- **Токен КП — единственная защита ссылки.** `crypto/rand`, не короче
  `MinQuoteTokenLength`. Не должен попадать ни в логи, ни в метрики: там
  пишется шаблон маршрута (`/v1/quotes/{token}`), а не путь.
- **Срок годности КП вычисляется, не хранится флагом** (`Quote.IsExpired`):
  флаг пришлось бы кому-то переключать, и до этого момента просроченное КП
  выглядело бы действующим. Истёкшее КП отдаётся с признаком, а не отказом.
- **Первое открытие КП отмечается один раз** — и доменом (`MarkOpened`),
  и условием `WHERE first_opened_at IS NULL` в запросе.
- **Программа лизинга опциональна.** Без неё КП считается по переданным
  вручную параметрам, и границы не проверяются вовсе.
- **Статус заявки меняется только через `Lead.TransitionTo`** по таблице
  `leadStatusTransitions`. `won` и `lost` терминальны: вернувшийся клиент —
  новая заявка, иначе история обращений схлопнется в одну строку.
- **Частота заявок ограничена по нормализованному номеру** (3 в час), а не
  по IP: за одним IP сидит офис или NAT оператора.

### Деньги и единицы

- Прайс каталога — центы USD (`price_usd_cents`), расчёт лизинга и КП —
  тиыны KZT (`*_kzt_cents`). Перевод один раз, в момент выпуска КП,
  по зафиксированному курсу.
- Доли — базисные пункты (`*_bps`): 18% это `1800`. Целые, а не проценты
  дробью, — участвуют в арифметике без ошибки округления, и взнос со ставкой
  оказываются в одной единице.
- Про представление дробных величин см. «Архитектурные границы».

## Миграции

**Только аддитивные.** Исходные миграции не правятся: скоро развёртывание,
и на живой базе переписать уже применённую миграцию нельзя — `golang-migrate`
считает её выполненной по номеру версии и повторно не запустит. Правка
исходника разъедет схему живой базы с той, что описана в репозитории,
и расхождение всплывёт на следующем развёртывании.

Отсюда следует:

- изменение схемы — **новая пара** `NNNN_имя.up.sql` / `.down.sql`;
- миграция обязана пережить существующие данные: колонка меняет смысл —
  добавь новую, перенеси значения, сними старую, и всё это в одной миграции;
- **`down` откатывает симметрично.** Не пустой файл и не «drop table»:
  откат обязан вернуть данные в прежний вид, иначе проверить миграцию
  на копии живой базы нечем;
- константы пересчёта (курс, коэффициент) пишутся в самой миграции
  с комментарием, откуда взялись: через полгода это единственное место,
  где сохранится основание.

Раньше действовало обратное правило — «править исходные, релиза не было».
Оно отменено.

## Структура проекта и организация модулей
- `cmd/app` — основная точка входа сервиса.
- `cmd/migrate` — прогон миграций PostgreSQL через `golang-migrate`.
- `internal/app` — сборка приложения, wiring зависимостей и запуск (`app.go`).
- `internal/config` — загрузка YAML/env-конфигурации.
- `internal/auth` — выпуск и разбор JWT доступа.
- `internal/domain` — ядро: `entity` (сущности домена, история изменений, доменные события, доменные ошибки), `form` (входящие DTO → сущность), `presenter` (сущность → исходящие DTO), `leasing` (чистый калькулятор лизинга, зависимостей внутри домена не имеет).
- `internal/service` — application services и use cases: `auth`, `catalog`, `fx`, `quote`, `lead`, `notification`, плюс общие `AuditRecorder` и `EventNotifier`.
- `internal/worker` — фоновые задачи: `fx` (загрузка курса), `outbox` (разбор очереди уведомлений).
- `internal/transport/http` — входящий HTTP-адаптер (chi). `resources/v1` — прикладные ручки (`auth`, `catalog_public`/`catalog_admin`, `quote_public`/`quote_admin`, middleware); `resources` — сервисные (`version`, `swagger`, `files`).
- `internal/storage` — исходящая персистентность: `postgres` (pgx/v5), `dragonfly` (Redis-совместимый кэш), `repository` (интерфейсы-порты) и `repository/mock_repo` (сгенерированные моки).
- `internal/swagger` — структуры метаданных для OpenAPI.
- `pkg` — переиспользуемые пакеты: `logger`, `cache` (+`cache/redis`), `httpx`, `apperrors`, `validate`, `clients/http` (HTTP-клиенты внешних сервисов), `metrics`, `repeatable`.
- `migrations` — SQL-миграции PostgreSQL (`golang-migrate`): `notification_outbox`, `users`, `catalog` (категории, характеристики, карточки, фотографии, значения), `fx_rates` (курсы и наценка), `leasing` (программы и КП), `leads`.
- `swagger` — сгенерированные OpenAPI-артефакты.
- `config` — YAML-конфигурация окружений.
- `integration-test` — Docker-based end-to-end тесты.

## Архитектурные границы
- `internal/domain` не зависит от транспорта, PostgreSQL, кэша, HTTP-клиентов и конфигурации.
- `internal/service` оркестрирует сценарии через домен и интерфейсы-порты (`internal/storage/repository`, `pkg/clients/http`); инфраструктура — за портами.
- `internal/transport/http` — парсинг транспорта, аутентификация и проверка роли, маппинг request/response, вызов сервисов.
- `internal/storage` реализует исходящие порты, пряча конкретные SDK и схемы хранения.
- Новые бизнес-правила сначала моделируй в домене; адаптеры только доставляют данные к use case и наружу.
- Аутентификация отделена от авторизации: `AuthMiddleware` выясняет, КТО пришёл, и кладёт актора в контекст; `RoleMiddleware` решает вопрос прав. Обработчики читают актора из контекста, а не из заголовков.
- Прикладные маршруты монтируются в группу за `srv.authMiddleware()` в `internal/transport/http/server.go`; сервисные (`/metrics`, `/version`, `/files`, `/swagger`) остаются снаружи.
- Статусы моделируй отдельными типами с явными переходами, а не строками: менять статус присваиванием поля нельзя.
- История изменений и уведомления — вспомогательные эффекты сценария: их отказ логируется и не откатывает бизнес-операцию (`AuditRecorder`, `EventNotifier`). События испускаются после коммита транзакции.
- Для nullable значений — общий `internal/domain/entity.Pointer[T]`. Локальные `stringPointer` не плоди.
- Деньги — целые минорные единицы (`int64`, суффикс `_cents`). Дробные величины
  (курсы, значения числовых характеристик) — `shopspring/decimal`.
- `decimal.Decimal` живёт внутри процесса: в `entity`, `form` и в сервисах,
  которые с ним считают. Наружу — в SQL, в кэш, в HTTP — он уходит **строкой
  фиксированной точности**, и точность задаёт домен одним методом
  (`entity.AppliedFXRate.String()`, `entity.NumberValue.String()`), а не
  вызывающий код. Причина: тип библиотеки в подписи адаптера сделал бы
  `shopspring/decimal` частью контракта хранилища, а `decimal.String()` без
  фиксированного хвоста делает `155` и `155.000` двумя написаниями одного
  значения — записанное перестаёт совпадать с прочитанным. `presenter`
  и `transport` про `decimal` не знают вовсе.
- `internal/domain/leasing` строже: `decimal` не появляется даже в его
  сигнатурах — на вход и выход только минорные единицы.

## Команды сборки, тестирования и разработки
- `make bin-deps` — установить `migrate`, `mockgen`, `swag`, `golangci-lint`, `gofumpt`.
- `make fmt` — форматировать через `gofumpt`.
- `make tidy` — `go mod tidy` + обновить `vendor/`.
- `make swag` — перегенерировать `swagger/` после изменений HTTP API.
- `make mock` — перегенерировать `gomock` моки после изменений интерфейсов.
- `make lint` — `golangci-lint run -v`.
- `make test` — `go test -cover -race ./internal/... ./pkg/...`.
- `make compose` / `make compose-down` — поднять/остановить PostgreSQL, Dragonfly, Pyroscope и сам сервис.
- `make migrate-up` / `make migrate-down` — миграции PostgreSQL; DSN задается через `DATABASE_URL`.
- `make integration` — интеграционный набор; не запускай (см. «Руководство по тестированию»).
- `make all` — полный цикл `fmt tidy swag mock lint test`; перед MR при изменении контрактов, генерации или зависимостей.

## Стиль кода и соглашения
- Go `1.26.x`. Форматирование и импорты оставляй `gofumpt`, `gci` и линтеру.
- Пакеты — нижний регистр; экспорт — `PascalCase`; внутренние хелперы — `camelCase`; тесты — `*_test.go`.
- Краткий комментарий к каждой новой/изменённой функции, типу, константе и переменной уровня пакета; для экспорта — начинай с имени идентификатора, для внутренних хелперов — объясняй маршрутизацию/побочный эффект/доменное действие, не повторяй сигнатуру.
- Ошибки обрабатывай явно. Избегай больших функций, магических чисел и `nolint`; если `nolint` неизбежен — точная причина.
- `swagger/`, моки и `vendor/` вручную не редактируй — `make swag`, `make mock`, `make tidy`.
- Линтер настроен с `run.tests: false`: использование только из `*_test.go` не спасает неэкспортированный код от `unused`.

## Руководство по тестированию
- Unit-тесты — рядом с пакетом; стандартный `testing`, `testify`, `gomock`.
- Для сервисов и портов — только сгенерированные `gomock` моки; рукописные стабы
  туда не добавляй. Исключение — тесты транспорта: там проверяется, ЧТО именно
  ушло в сервис, а не сколько раз его позвали, поэтому заглушка запоминает
  аргументы и подменяет ответ (образец — `stubCatalogService`, `stubQuoteService`).
  Заглушка встраивает интерфейс сервиса и переопределяет только нужные методы:
  добавление метода в интерфейс не ломает чужие тесты.
- Table-driven держи читаемыми; для каждого исправленного поведения — регрессионный кейс.
- `require` — для setup-ошибок, конструкторов, `nil`-проверок и условий, после которых тест невалиден.
- `assert` — только для независимых нефатальных проверок, где продолжение даёт полезную диагностику.
- Один `require.Equal` для полной стабильной структуры лучше множества проверок отдельных полей.
- Момент времени в тестах токенов считай от `time.Now()`, а не фиксированной датой: фиксированная дата делает тест зелёным ровно `TokenTTL` и потом ломает его на истёкшем токене.
- Интеграционные сценарии (`make integration`, `go test -tags integration ...` и аналоги) не запускай — они зависят от Docker Compose сервисов этого репозитория, пользователь запускает их сам.
- При изменении контракта эндпоинта область поиска затронутых мест — путь
    маршрута (rg по фрагменту URL), а не имена helper'ов: один эндпоинт может
    дёргаться из нескольких helper'ов и напрямую.
- Утверждение «интеграционный набор готов к прогону» без прогона не делается.
  Если изменение ломает контракт, задача заканчивается просьбой к пользователю
  запустить make integration и приложить результат.

## Коммиты и merge request'ы
- Коммит: ключ задачи, опциональный scope, краткое описание в повелительном наклонении. Пример: `RD-226 storage: перевести хранилище на PostgreSQL`.
- Рефакторинги держи отдельно от изменений поведения.
- MR описывает цель, рискованные зоны, задачу и локальную верификацию (`make lint`, `make test`, при необходимости `make integration`).
- При изменении API-контрактов перегенерируй `swagger/` и упомяни это в MR.
- **Никогда не добавляй `Co-Authored-By: Claude` и любые другие трейлеры Claude Code в коммиты.**
